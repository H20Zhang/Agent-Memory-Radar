# Demystifying Agent Skills: Why They Work—Until They Don’t

**arXiv:** [2608.14036](https://arxiv.org/abs/2608.14036) · **Published:** 2026-08-14 · **Category:** Evaluation & Analysis · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `procedural` `text` `coding` `general-agent`

> **TL;DR.** This paper turns skill evaluation from “did success improve?” into a controlled decomposition of **representation → retrieval → invocation → execution**. With the same source trajectories, standardized skills outperform direct Workflow Memory and mostly work as **procedural anchors**, while retrieval accuracy remains a poor proxy for downstream utility.

## Problem

Agent skills are often treated as successful whenever aggregate task success rises. That hides several causal questions: did the representation itself help; did outcome annotations matter; did the artifact transfer across frameworks; was the right skill found; and, even if it was found, did the agent use it in a way that actually changed execution?

The resulting “skill works” claim is too coarse to guide memory design.

## Core idea

The paper builds matched experiments around the **same prior trajectories**. It compares Raw execution, cleaned **Workflow Memory**, and standardized **SKILL.md** artifacts; removes explicit success/failure hints; transfers artifacts across agent frameworks; and separates three retrieval measurements—embedding ranking, explicit agent selection, and full-pool execution-time skill use.

The second layer is contrastive trajectory analysis: instead of labeling a run only as pass/fail, it codes *how* injected prior experience changed behavior.

## Memory design

| Stage | Design under study |
|---|---|
| Write | Distill matched successful/failed trajectories into Workflow Memory or SKILL.md; optionally remove outcome labels to isolate their contribution. |
| Organize | Represent reusable prior experience either as cleaned trace-like workflow memory or as a standardized procedural skill artifact. |
| Read | Evaluate embedding retrieval, explicit selection, actual execution-time access, and downstream success separately rather than treating one retrieval metric as the whole pipeline. |
| Update / forget | No online consolidation/forgetting policy; the paper analyzes fixed constructed skills, transfer, retrieval, and use rather than long-running evolution. |

## Compared to what

The cleanest comparison is **Skill vs Workflow Memory built from exactly the same source trajectories**. That is stronger than comparing a skill system against no memory or against a different experience corpus, because it asks whether the *representation* changes reuse quality.

A second comparison separates **retrieval correctness** from **execution utility**: a ground-truth skill can be selected and still fail, while a related non-ground-truth skill can still help.

## Evidence

Across matched comparisons, Skills improve over Workflow Memory by **6.06 points**. The trajectory taxonomy is more diagnostic than the headline score: **procedural anchoring accounts for 65.7% of skill cases**, while explicit knowledge injection accounts for only **4.5%**. The main effect is therefore stabilizing setup, tool sequence, implementation routine, and verification—not supplying missing facts.

Retrieval exposes a different bottleneck. As candidate pools grow from **5 → 100**, actual-use precision falls from **29.6% → 3.3%**, yet downstream success is comparatively stable. Exact ground-truth invocation is therefore **neither sufficient nor necessary** for successful execution.

The qualitative taxonomy is also unusually well checked: the study normalizes **8,135 trials**, retains **238 valid coded labels**, and reports **95.8%** exact human/LLM aggregation agreement with **Cohen’s κ = 0.952**.

## Why it matters

This sharpens two current radar claims.

First, **procedural memory is not just compressed knowledge**. Its main value can be an action anchor that removes noisy exploration and stabilizes execution.

Second, **retrieval success ≠ reuse success**. A memory system that optimizes only skill-selection precision can miss useful related procedures and can still fail after retrieving the nominally correct artifact.

The right evaluation unit is therefore the stage boundary: representation quality, retrieval, invocation/adaptation, and downstream execution need separate controls.

## Limitations / questions

- Evidence is concentrated in terminal/software-oriented tasks and a small number of framework/model pairings; broader domain transfer is still open.
- The three retrieval arms are intentionally independent diagnostics, not one end-to-end learned retrieval system.
- The study evaluates constructed skill libraries rather than months-long libraries whose content, router, and governance co-evolve.
- Poor ground-truth retrieval does not necessarily mean poor practical retrieval because related non-ground-truth skills can help; benchmark labels may therefore under-specify procedural relevance.

**Curator take:** **4/5**. The contribution is not another skill construction method. It is a controlled methodology that separates *why a procedural artifact helps* from whether a benchmark score moved, and it provides unusually strong evidence that representation and retrieval metrics should not be collapsed into one “skill memory” score.
