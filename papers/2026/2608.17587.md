# Write, Execute, Refine: From Skill Followers to Skill Optimizers via Reinforcement Learning from Execution Feedback

[Latest Papers](../../README.md#latest-papers) · [Research Map](../../README.md#research-map) · [Memory Learning & Evolution](../../categories/memory-learning-evolution.md)

**Paper:** [arXiv:2608.17587](https://arxiv.org/abs/2608.17587) · **Published:** 2026-08-18 · **Importance:** 4/5 · **Confidence:** High  
**Tags:** `procedural` `text` `general-agent` · **Code:** [littlepkk/WER4skill-optimizer-training](https://github.com/littlepkk/WER4skill-optimizer-training)

> **Research delta.** WER trains the **skill writer itself** from execution consequences: a frozen agent executes candidate skills, programmatic verifiers score outcomes, and matched success/failure trajectories become the next refinement state. This is stronger supervision than asking an LLM to reflect on its own prose.

## Problem

Expert skills can help tool agents, but agent-authored skills can underperform no-skill execution. The missing capability is not necessarily following a skill; it is **learning how to improve a skill from what actually happened when the agent used it**.

Inference-time refinement loops can repair one artifact without teaching the model that writes the next artifact. They also lack a clean credit signal when several rewritten skills sound plausible.

## Mechanism

WER places a trainable Skill Optimizer outside a frozen executor. The optimizer proposes candidate skill documents; the same frozen agent executes each candidate repeatedly; programmatic verifiers score the outcomes; group-relative RL updates the optimizer.

For later phases, WER keeps cases where the same skill/task produced both success and failure. The matched trajectories become the diagnostic context for the next refinement state:

`current skill → candidate skills → frozen executions → verifier scores → relative RL → mixed-outcome records → next refinement state`

## Compared with

The strongest control is **the same Qwen3-4B optimizer backbone under the same refinement workflow but without optimizer training**. That isolates learning the skill-writer policy from simply running a capable model inside a refinement loop.

No-skill, seed-skill, general-purpose optimizer models, and refinement-depth checkpoints provide additional boundaries.

## Decisive evidence

On BFCL v4, No Skill is **68.83**, seed skill **67.28**, the untrained 4B optimizer **67.28**, and WER-trained 4B **76.63**—a **+9.35** point gain over the same untrained optimizer. On tau2, the matched comparison is **40.43 → 50.72 (+10.29)**.

The refinement-depth result is equally useful: BFCL improves through the trained phases, but an additional refinement step falls from **76.63 to 75.33**. More self-editing is not monotonically better.

## Main caveat

WER assumes expensive training-time execution: repeated rollouts, stateful tool environments, and programmatic verifiers. Domains without reliable execution feedback do not automatically inherit the benefit.

The final protocol also uses a stronger model for domain-skill merging, so the full artifact pipeline is not solely the learned 4B optimizer. Evaluation remains two tool-agent benchmark families rather than an open-ended evolving skill ecosystem.

## Memory lifecycle

| Stage | Design |
|---|---|
| Write | Trainable optimizer writes/refines natural-language skill artifacts. |
| Organize | Persistent procedure is the skill document; execution histories form diagnostic refinement state. |
| Read | Frozen executor consumes the current skill; optimizer consumes matched execution evidence. |
| Update / forget | Group-relative RL updates the writer policy and iterative phases update the skill; deeper refinement can regress, but general deletion/governance is not studied. |

## Why it matters

WER shifts procedural-memory evolution from **artifact editing** to **learning a state-transition policy from downstream execution**. The comparison to the same untrained optimizer makes that boundary unusually clear.
