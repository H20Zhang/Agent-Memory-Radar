# ArborMem: Navigating Interaction States with Memory Forests

[Latest Papers](../../README.md#latest-papers) · [Research Map](../../README.md#research-map) · [Retrieval & Access](../../categories/retrieval-access.md)

**Paper:** [arXiv:2608.17534](https://arxiv.org/abs/2608.17534) · **Published:** 2026-08-18 · **Importance:** 4/5 · **Confidence:** High  
**Tags:** `episodic` `hierarchical` `timeline` `general-agent`

> **Research delta.** ArborMem inserts **state localization before retrieval**: determine which historical interaction state the current turn resumes, restore that branch-local trajectory, then retrieve only supplemental evidence. It therefore separates “where am I in history?” from “what memories are relevant?”

## Problem

Long-running conversations interleave tasks, people, plans, and revisions. A similarity retriever can find topically related history while still selecting the wrong trajectory state—for example, an earlier version of a project rather than the branch the user just resumed.

This makes ordinary relevance retrieval under-specified: **relevant to which interaction state?**

## Mechanism

ArborMem represents a conversation as a forest whose nodes are interaction states. Explicit continuation/temporal cues can take a fast path; otherwise the system retrieves candidate states and reranks them using topic keys, path summaries, node summaries, and entities.

After choosing a parent state:

`new turn → localize parent state → restore root-to-parent branch trajectory → retrieve supplemental cross-branch facts/records → answer → commit new state`

The write occurs after generation, preserving the causal distinction between evidence used for the current response and state created by that response.

## Compared with

The most diagnostic internal control removes **state localization** on a fixed LongMemEval subset while leaving the rest of the memory stack available. Atomic-fact retrieval is ablated separately, which helps distinguish branch navigation from general evidence extraction.

The external comparisons span LongMemEval, LoCoMo, BEAM100K, and the paper's BranchMemEval diagnostic for interleaved/resumable trajectories.

## Decisive evidence

ArborMem reports gains over the strongest compared baseline of **+9** points on LongMemEval, **+10.31** on LoCoMo, **+3.36** on BEAM100K, and **+5** on BranchMemEval; on BranchMemEval it is also **15 points above full context**.

On a fixed 50-question LongMemEval subset, removing state localization drops the 30B setting **82 → 70**, but the 4B setting only **48 → 46**. Removing atomic-fact retrieval drops the 30B setting further to **62**. State localization matters, but it is not the whole gain and its effect is model-dependent.

## Main caveat

The full system changes several things together: forest structure, summaries, atomic facts, structured records, and prompts. The evidence supports the **state-localization boundary** more cleanly than it supports the claim that a forest is the uniquely right representation.

The single-parent assumption is also fragile for multi-intent turns, and a wrong routing decision can become persistent structure for future turns. BranchMemEval is useful but small and synthetic.

## Memory lifecycle

| Stage | Design |
|---|---|
| Write | After generation, commit a new state node plus facts/records with provenance/revision metadata. |
| Organize | Forest of branch-local interaction states plus supplemental facts/records. |
| Read | Localize active parent state, restore branch trajectory, then retrieve cross-branch support. |
| Update / forget | Extend/create branches and revise records; robust branch repair, aging, and deletion are not central. |

## Why it matters

ArborMem suggests that “memory retrieval” should be split again: **state localization → state restoration → supplemental evidence retrieval**. That decomposition is especially relevant for agents that repeatedly pause and resume long-lived projects.
