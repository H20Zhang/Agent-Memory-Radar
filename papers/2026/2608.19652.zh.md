# Agent Memory 能否跟踪持续变化的状态？

[English](2608.19652.md) · [← 最新论文](../../README.md#latest-papers) · [领域地图](../../README.md#research-map) · [写入、更新与整合](../../categories/zh/write-update-consolidation.md)

**Paper:** [arXiv:2608.19652](https://arxiv.org/abs/2608.19652) · **Published:** 2026-08-20 · **Importance:** 4/5 · **Confidence:** Medium
**Tags:** `semantic` `structured` `timeline` `general-agent`

> **Research delta.** StateMemBench 不再把“当前值”和“已被取代的旧值”都算作 retrieval success，而是分别评分。StateMem 显式处理 supersession 与 recomputation；但 dependency propagation 并不稳定，最强的 matched result 来自另一个 answer-time full-transcript wrapper，而不是 persistent store。

## Problem

Memory system 可以取回所有相关事实，却仍根据旧 budget、已撤销约束，或输入已经变化的 derived value 行动。以 recall 为主的 benchmark 很少单独识别这种 state drift。

## Mechanism

StateMemBench 包含 234 个 synthetic multi-session scenario、322 个 probe。Deterministic event program 计算当前 operative state；几种 executable lazy-reader policy 生成合理但过时的答案。Closed-pool grading 把结果分为 `gold`、`drift`、`other` 与 `off-pool`。

Persistent StateMem 写入带 source、priority 和 typed dependency 的 state unit。Superseded unit 保留用于 audit，但不再参与回答。Deterministic rechecker 把受影响的 dependent unit 标为 `needs_recheck`；最终一次 answer call 接收 active state 与 recomputation guidance。

StateMemWrapper 是独立实验。它没有 store，也没有 per-turn processing；回答时读取完整的 numbered transcript 与同一 backend 的 retrieved chunk，先写 query-conditioned value chain，再处理 precedence 并重算当前状态。

## Compared with

Persistent system 最接近的对照是 staged ablation：extraction-only、extraction 加 supersession、full 减 dependency propagation、full 减 recomputation guidance。Cross-system comparison 还包含同 backbone 的 long context、retrieval、graph-RAG 和四种 memory system。

Wrapper 的最强 control 固定 backend、retrieved chunk、full transcript、一次 answer call、250-word intermediate budget、commit-before-answer format 与 judge，只把显式 state tracing 换成 generic question-conditioned summary。

## Decisive evidence

在 DeepSeek-V4-Flash 上，persistent StateMem 为 **0.363**，Dense 为 **0.205**、A-Mem 为 **0.199**。Extraction-only 是 **0.174**；加入 supersession 达 **0.298**；去掉 recompute guidance 降至 **0.301**。Dependency propagation 没有全局增益：移除后反而 **0.363→0.373**，并避免 Set-B anti-trap 上 **12.5 分**的损失。

在 Qwen 上，StateMem 为 **0.233**、Mem0 为 **0.149**，但与 GraphRAG **0.224** 无显著差异（paired McNemar **p=0.82**）。外部 benchmark 的结果更窄：DeepSeek 上，LongMemEval 为 **0.656 vs long context 0.666**，LoCoMo 为 **0.592 vs 0.587**；增益集中在与 drift 相关的 question type。

对六个 backend，StateMemWrapper 在 StateMemBench 上相对 matched generic-summary control 增加 **15.0–31.7 分**。这有力支持 query-conditioned state resolution，但 wrapper 读取完整 transcript，本身不是 persistent memory。

## Main caveat

这个 synthetic benchmark 围绕 StateMem 同一套 supersession/recomputation policy family 生成并筛选，因此自建 benchmark margin 是 in-distribution upper bound。每个配置只有一次 run，统一由一个 DeepSeek-family judge 评分；部分 released baseline 还产生大量 non-answer。

成本会改变结论。Persistent StateMem 每个 scenario 约需 **165–600 次 ingestion LLM call**，但 token、latency、美元、store growth、maintenance 与 amortization 均未报告。Wrapper 不做 ingest，却要读取中位 **8.6k / 87k input-token transcript**，每题还比 control 多约 **350 token**。论文没有测 tool execution 或 multi-step action outcome。

## Memory lifecycle

| 阶段 | 设计 |
|---|---|
| Write | 每个 conversation turn 用一次 TurnEncoder LLM call 写入带 source 的 state unit。 |
| Organize | 以 priority、date 和 dependency 区分 active、superseded、needs-recheck unit。 |
| Read | 把 active state 提供给最终 answer call；独立 wrapper 则扫描 full transcript。 |
| Update / forget | 让 superseded unit 退出使用但保留 audit history，并标记 dependent value 等待重算。 |

## Why it matters

Current-state resolution 是不同于 recall 的 lifecycle boundary。Benchmark 应惩罚“历史取对了、当前 operative state 却用错了”的答案。这篇论文为 supersession 和 query-conditioned resolution 提供了重要 early evidence，但不能证明 structured persistent memory 普遍优于简单系统。
