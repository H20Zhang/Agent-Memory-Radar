# ERSkill: Evolving for Skill-Guided Adaptive Memory Retrieval

**arXiv:** [2608.12720](https://arxiv.org/abs/2608.12720) · **Published:** 2026-08-13 · **Category:** Memory Learning & Evolution · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `procedural` `structured` `general-agent`

> **TL;DR.** ERSkill makes the **memory read policy itself evolvable**: retrieval behaviors become executable skills, and the skill set co-evolves with a query-conditioned router so strong new capabilities are deployed only when the controller can reliably activate them.

## Problem

Many self-evolving memory systems revise stored summaries, experiences, or prompts while leaving query-time access behavior fixed. That is a hidden constraint: heterogeneous questions can require different evidence-construction procedures even when the underlying memory store is unchanged.

## Core idea

Express retrieval behaviors as executable skills composed from a fixed primitive library. Record explored primitive paths in an experience trie, propose improved skills from rollout evidence, maintain a broad capability frontier and a conservative deploy frontier, and jointly update a learned router that chooses which skill should serve each query.

## Memory design

| Stage | Design |
|---|---|
| Write | Compile histories into structured memory atoms; LLM construction is used mainly for relation extraction rather than repeatedly rewriting full history. |
| Organize | Keep memory atoms separate from executable retrieval skills. An experience trie stores explored skill paths; capability/deploy frontiers retain non-redundant retrieval programs. |
| Read | A learned query-conditioned router selects one retrieval skill; the skill executes retrieval/evidence-processing primitives while maintaining evidence state for answer generation. |
| Update / forget | Training generates candidate skills from rollout traces, updates the router/frontiers, and records accept/reject outcomes. Weak/redundant skills can leave the frontiers; underlying user-memory forgetting is not studied. |

## Compared to what

ERSkill compares with non-evolving memory systems such as **A-Mem, MemoryOS, and LightMem**, and self-evolving experience/prompt systems including **Dynamic Cheatsheet, ReasoningBank, GEPA, and MemSkill**. The more diagnostic internal comparisons remove skill evolution, replace the learned router, or simplify the frontier/search machinery.

## Evidence

Across LoCoMo, LongMemEval, and PerLTQA, ERSkill reports the strongest average under both Qwen3-Next-80B-A3B-Instruct and GPT-5.4-nano. With Qwen, average **F1 / BLEU-1 / LLM-Judge = 49.55 / 49.19 / 61.30**; with GPT-5.4-nano, **40.97 / 37.62 / 61.11**. The paper reports **31.3%** and **28.1%** relative improvement in its overall metric average over the strongest baseline.

The transfer result is particularly relevant: on LongMemEval, the router and retrieval skills trained on LoCoMo are reused **without additional training** and still lead the reported table for both backbones. Ablations show the largest losses when **skill evolution** or the **learned router** is removed; the double frontier and experience trie make smaller contributions to stability/search efficiency.

## Why it matters

ERSkill moves self-evolution from **what is stored** to **how memory is read**. That is a distinct control boundary: the archive can remain fixed while the agent learns which evidence-construction program to execute. The deploy frontier also exposes a practical point—an oracle-good retrieval skill has little value if the router cannot reliably select it.

## Limitations / questions

- Skill evolution is training-time expensive because it depends on repeated rollout evaluation and LLM-as-a-Judge supervision.
- The primitive library is fixed, so evolution searches compositions of known operations rather than inventing fundamentally new access operators.
- Evaluation remains long-term memory QA rather than planning, tool use, or interactive decision-making.
- Headline gains combine memory construction, executable-skill search, frontier governance, and router learning; they should not be attributed to one component alone.

**Curator take:** **4/5**. The novel boundary is stronger than the exact benchmark gain: **retrieval policy becomes persistent, versioned, evolvable state**. The main open question is whether that machinery transfers beyond QA strongly enough to justify its training cost.
