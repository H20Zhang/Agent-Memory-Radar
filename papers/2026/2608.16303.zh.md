# FTA-Mem：Memory Granularity 作为 Workload Parameter

**中文** | [English](2608.16303.md) · [返回首页](../../README.md) · [Research Library](../../library/README.md)

[Paper](https://arxiv.org/abs/2608.16303) · **Importance: 3/5**

> **Research delta.** FTA-Mem 最值得保留的结论不是一种新的 memory unit，而是：**write granularity 会随 dialogue evidence density 改变**。Session 太粗，turn-pair 又可能过细且昂贵；不存在明显的“一种单位 everywhere 最优”。

## Problem

长期对话里，memory unit 既不能无限大，也不能无限小。Session-level representation 会把不相关信息捆在一起；turn-pair memory 保留细节，却产生大量冗余、construction token 与 retrieval burden。

稀疏长期对话尤其放大这个问题：真正有用的 evidence 间隔很远，用固定 session 或每 turn 都写 memory 都不理想。

## Mechanism

FTA-Mem 构建 situation-level windows，并围绕 Fact / Time / Affect 组织持久化单元：

`dialogue → boundary-preserving situation windows → FTA units → carry/fuse unresolved boundary evidence → temporal links → retrieve structured context`

它试图让一个 memory unit 对应“语义上相对完整的 situation”，同时处理跨 boundary 的未完成 evidence。

## Closest comparison

最有价值的比较是直接控制 granularity：session-level、turn-pair、FTA-Mem。

这比只和另一套复杂 memory system 比更接近因果问题，因为它问的是：**同一个 workload 下，一个 persistent unit 应该多大？**

## Decisive evidence

ES-MemEval：

- session: **31.76 F1 / 1.58M construction tokens**
- turn-pair: **37.06 / 6.40M**
- FTA-Mem: **38.71 / 4.99M**

LoCoMo 上则出现反转：turn-pair **38.28 F1** 略高于 FTA-Mem **37.35**，但 construction token 为 **7.04M vs 3.39M**。

这组结果直接说明 granularity 是 quality–cost trade-off，而且 workload density 会改变 preferred point。

## What remains unproven

FTA-Mem 仍然使用一套全局 segmentation policy。更强的系统问题是：**能否根据在线 evidence density、conflict、query pattern 与 budget 动态选择 memory-unit granularity？**

还需要把 construction token 之外的 storage、retrieval latency、update cost 和 downstream acting quality 一起纳入。

## Field-map consequence

Write side 不应只有“写什么”，还应显式包含：

`boundary / granularity × preservation contract × update frequency`

这些是不同控制变量。
