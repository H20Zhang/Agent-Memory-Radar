# Break It Down, Pass It On: Cross-Task Skill Transfer in LLM Agents

> **Research delta.** The write unit changes transfer: whole-task text and code skills reduce average success, while subtask skills produce small average gains. The result is heterogeneous and consumer-dependent, not a universal subtask advantage.

## Problem

Skills induced from completed trajectories can carry incidental details or overly broad procedures into later tasks. Granularity may control reuse, but finer units also create more writes and retrieval calls.

## Mechanism

After each task or subtask, one LLM call writes a persistent text workflow or Python function. Description embeddings retrieve top five skills above a threshold on later distinct tasks. Text skills may merge; code may overwrite/deduplicate, load into the namespace, and trigger cascading prune if dependencies fail.

## Compared with

Task-level text/code memory is compared with the same task actor without memory; subtask memory has its own matched no-memory actor. A stronger two-model check freezes the subtask-generated library and replays it into the task actor, reducing consumer confounding. Text versus code is not representation-only because code gains executable loading and different maintenance rules.

## Decisive evidence

Across 11 models and 809 tasks, Task no-memory/Text/Code scores **22.1 / 20.9 / 18.0%**; Subtask no-memory/Text/Code scores **24.8 / 26.7 / 25.3%**. Earlier skills are retrieved on later tasks and official environment evaluators score the final state, so persistent memory directly changes behavior.

The frozen-library replay reports task actors using subtask skills **+9.9pp** on average across two models. Yet task-bootstrap intervals overlap, many model/domain cells reverse, and the proposed utility score has only weak within-difficulty association.

## Main caveat

Task and subtask agents differ in planner, summarizer, query frequency, write count, and the trajectories that seed their libraries. Task order is undocumented; there are no repeated stochastic seeds or paired primary tests. The stated artifact contains no implementation or data when verified.

Latency and MEM1 dependency curves cover execution cost, but full induction, embedding, library growth, context injection, dependency loading, merge/prune, tokens, dollars, storage, and energy are unreported.

## Memory lifecycle

| Stage | Design |
|---|---|
| Write | One skill is induced from each completed task or subtask trajectory. |
| Organize | Description embeddings, merge/overwrite, deduplication, and dependency pruning maintain the library. |
| Read | Top-5 text or executable code skills reach the later actor. |
| Update / forget | Libraries evolve condition-specifically; broken code and dependents can be pruned. |

## Why it matters

Procedural-memory design should treat granularity as a causal policy and test it with the same consumer. More elaborate or executable skills can be worse than no memory.
