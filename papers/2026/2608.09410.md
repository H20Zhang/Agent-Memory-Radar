# Skills in Weights, Memory in Code: Hybrid Learning for Memory-Dependent Robot Manipulation

**arXiv:** [2608.09410](https://arxiv.org/abs/2608.09410) · **Published:** 2026-08-10 · **Category:** Memory Learning & Evolution · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `working` `procedural` `structured` `embodied`

> **TL;DR.** HyMeS learns reusable motor skills in VLA weights but learns long-horizon memory strategy as executable code. Symbolic task state selects differentiable constraints that steer a frozen VLA's action denoising; multimodal execution feedback then updates that state.

## Problem

Memory-dependent manipulation is non-Markovian: the same current observation can demand different actions because of a cue, count, or stage remembered from earlier in the episode. End-to-end memory-augmented VLAs can absorb history into the action model, but that couples memory acquisition to motor learning and requires demonstrations across combinatorial memory configurations even when the physical skill is unchanged.

## Core idea

HyMeS splits the learning substrate. A Markovian flow-matching VLA is fine-tuned only for reusable motor skills. Separately, a coding agent uses rollout traces and stage verdicts to iteratively edit an executable program containing **constraint-selection, event-verification, and memory-update rules**. At runtime the program maintains symbolic task state; that state selects a differentiable stage constraint whose gradient is injected into VLA denoising. PACE closes the loop by verifying progress from proprioception plus multi-frame VLM evidence before advancing memory.

## Memory design

| Stage | Design |
|---|---|
| Write | Development rollouts produce symbolic traces and stage outcomes; a coding agent revises the executable memory program. Episode initialization instantiates symbolic state from instruction + observation. |
| Organize | Program = constraint-selection + verification + update rules. Runtime state stores plan, active stage, bindings, repetition counters, and persistent interaction state. |
| Read | The active memory state chooses a differentiable constraint; its gradient steers the frozen flow-matching VLA's action generation. |
| Update / forget | PACE accepts stage events from proprioceptive + multi-frame VLM evidence, then advances state and updates bindings/counters. Program learning is frozen at evaluation; no long-term forgetting policy is studied. |

## Compared to what

The strongest empirical comparison uses the **same-weight pi0.5** reactive policy and **PrediMem** reevaluated on the same corrected 12-task RoboMemArena protocol. Conceptually, HyMeS also challenges end-to-end memory VLAs: it keeps history-dependent strategy outside the policy weights and learns it from rollout feedback rather than expert actions covering every memory configuration.

## Evidence

On the corrected **12-task / 160-episode RoboMemArena** protocol, HyMeS reports **66.2% CSR / 60.1% TSR**, versus **52.5% / 41.3%** for pi0.5 and **61.7% / 45.6%** for PrediMem. On SO-101, TSR rises **25.7% → 57.1%**. The paper reports that rollout experience contributes **+8.5 CSR / +18.4 TSR**, while combining proprioceptive and visual completion evidence improves stage-transition reliability over either signal alone.

The key causal interpretation is narrower than the headline: the evidence supports **external executable memory + steering under fixed VLA weights**, not a general claim that code-space memory always beats learned memory modules.

## Why it matters

The durable design point is **substrate separation**. Long-horizon task state can live in inspectable code while motor competence stays in weights, and memory can intervene *inside* action generation rather than only at high-level orchestration. That is a stronger architectural claim than “robots need memory.”

## Limitations / questions

- The benchmark uses a corrected 12-task subset chosen to isolate history-dependent failures; broader RoboMemArena generality is not established.
- The memory program is improved on development rollouts and **frozen during evaluation**; this is not continual online program evolution at deployment time.
- PACE depends partly on Qwen3-VL-8B completion judgments and fixed voting parameters, so update correctness inherits verifier errors.
- Cross-policy, cross-robot, and open-ended transfer of the learned memory program remains untested.

**Curator take:** **4/5.** The important result is the weights-vs-code boundary plus a closed memory→action→verification loop under fixed policy weights. The evidence is strong enough to be notable, but still concentrated on a deliberately filtered manipulation regime.
