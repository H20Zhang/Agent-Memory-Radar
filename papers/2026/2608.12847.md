# Beyond Retrieval: Query-Conditioned Reuse of Long-Horizon Agent Trajectories

**arXiv:** [2608.12847](https://arxiv.org/abs/2608.12847) · **Published:** 2026-08-13 · **Category:** Representation & Organization · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `procedural` `text` `web-agent`

> **TL;DR.** QCR identifies a distinct post-retrieval bottleneck: once a relevant long trajectory has been selected, the agent still needs a target-bound representation that preserves reusable procedure while forcing stale source bindings to be reacquired from current state.

## Problem

Retrieval answers **which past trajectory may help**. It does not answer **how the current agent should use it** when users, files, object IDs, dates, constraints, or environment state have changed. Injecting the full source trace can copy stale values into the new task; a source-only summary can be shorter but still does not explicitly say what must be rebound or when the prior procedure no longer applies.

The paper therefore isolates reuse after retrieval rather than proposing another store or retriever.

## Core idea

QCR inserts one operation after a memory has already been selected. From the selected trajectory, target query, and initial target observation, it produces a compact support object with four fields:

1. **Workflow invariant** — the reusable action/decision pattern.
2. **Bindings to re-obtain** — source-specific entities, paths, IDs, dates, or parameters that must be recovered from current evidence.
3. **Applicability conditions** — conditions under which reuse should be declined.
4. **Verification guardrail** — the check required before declaring completion.

The acting agent still has to ground current values from the query, observation, or later tool calls. QCR is deliberately a diagnostic intervention: if the same selected trajectory helps more after this transformation, the missing operation is post-retrieval reuse rather than storage alone.

## Memory design

| Stage | Design |
|---|---|
| Write | Cache successful source trajectories plus compact descriptors; generic source summaries are constructed offline. |
| Organize | Keep the persistent bank unchanged; QCR creates a short target-bound procedural support object after selection. |
| Read | Fixed top-5 embedding retrieval → compact-summary reranking → one selected memory → deliver Full Trajectory / Generic Summary / QCR / No Memory under matched target conditions. |
| Update / forget | Not studied; the experiment concerns reuse of verified historical trajectories, not lifecycle editing. |

## Compared to what

The strongest experimental property is the accounting boundary. Candidate retrieval, target state, acting model, decoding, and tool budget are held fixed while only the representation of the **same selected memory** changes.

The key baselines are **Full Trajectory** and a length-matched **Generic Summary**. This makes the result much stronger than comparing QCR to a different memory pipeline whose retrieval quality also changed.

## Evidence

Across **2,391** WebArena, WorkArena, and AppWorld targets, QCR reaches **62.3%** average Success, **+10.7pp** over Full Trajectory, while using **9.4k** online tokens versus **18.4k** for direct trajectory injection (**−48.9%**).

Selection is already strong: summary reranking selects reusable history for **94.8%** of targets and QCR success is only **1.8pp** below an oracle reusable selector. That matters because it moves the likely bottleneck downstream of retrieval.

The binding-shift analysis is particularly diagnostic. Under large rewrites, stale-binding errors fall **46.9% → 10.9%** and correct rebinding rises **31.7% → 77.8%** relative to Full Trajectory. Utility under large shift is **+20.1pp** for QCR versus **+2.2pp** for the raw trajectory.

## Why it matters

Long-horizon procedural memory has a third stage that many systems blur together: **retrieve → select → adapt for current state**. A complete trajectory can be excellent archival evidence and still be the wrong actor-facing interface. This suggests persistent stores should preserve provenance-rich source records while the acting context receives a separately constructed, target-bound reuse object.

## Limitations / questions

- The source memories are successful trajectories; partial failures and naturally accumulated histories are not tested.
- Only one selected memory is injected, so multi-memory composition remains open.
- The four QCR fields are not independently ablated; the evidence supports target-conditioned reuse more strongly than this exact schema.
- Verified completion does not capture irreversible side effects or policy violations caused by reuse.

**Curator take:** **4/5**. The importance is the experimental separation of retrieval from reuse. Compared with another memory representation paper, this one gives a cleaner answer to “where is the bottleneck?”—after a good trajectory is retrieved, adapting it to current bindings can dominate the remaining gap.
