# Skill2Query: Exploiting Skill Structure to Generate Pseudo-Queries for Agent Skill Retrieval

[← Latest Papers](../../README.md#latest-papers) · [Research Map](../../README.md#research-map) · [Retrieval & Access](../../categories/retrieval-access.md)

[arXiv 2608.16071](https://arxiv.org/abs/2608.16071) · Published 2026-08-17 · Importance **3/5** · Confidence **high** · [Code](https://github.com/MatZaharia/Skill2Query)  
`procedural` `structured` `text` `general-agent`

> **Research delta.** Skill2Query aligns procedural-memory retrieval supervision with **capability + parameter structure** inside a skill rather than treating the whole skill document as one semantic blob; the gain is strongest offline, while serving-time query expansion is inconsistent.

## Problem

Users describe goals in task language, while SKILL.md-style artifacts describe developer-facing capabilities, parameters, constraints, and usage examples. Whole-document retrieval or document-level pseudo-query generation can therefore match the right topic but miss the actual callable capability or generate an invalid parameterization.

The challenge becomes more acute as the skill library grows and manually labeling query→skill pairs becomes expensive.

## Mechanism

Skill2Query parses each skill into a **Skill Knowledge Graph** connecting capabilities, parameters/constraints, and examples. It then generates pseudo-queries by imitating user-query style, anchoring templates to specific capabilities, and filling/validating parameter slots.

`skill document → capability/parameter/example structure → pseudo-queries → offline augmentation / online expansion / retriever training → selected skill`

The goal is functionally grounded retrieval supervision, not merely text that looks semantically similar to the outer document.

## Compared with

Pseudo-query generation is compared with **Zero-shot LLM**, **Few-shot LLM**, and a SkillFlow-style full-text condition. Retrieval is tested with BM25, a dense retriever, and SkillRouter under baseline/offline/online variants.

The most informative comparison is the **SKG ablation**, because it asks whether explicit capability/parameter structure improves synthetic supervision quality.

## Decisive evidence

On ToolQA, offline augmentation raises SkillRouter Recall@1 from **35.80% → 47.34%** and dense retrieval from **13.22% → 29.79%**.

The cleaner generation ablation is:

- Exec-Pass: **42.85% → 22.63%** without the Skill Knowledge Graph;
- functional coverage: **11.32% → 2.41%** without the graph.

Serving-time expansion is not uniformly positive: some settings improve, while several LogicBench/ToolQA cells degrade. The right takeaway is therefore that **offline supervision and online expansion solve different regimes**.

## Main caveat

End-to-end evidence remains narrow. The downstream case study is one-step skill injection rather than long-horizon tool use with invocation, failure recovery, and evolving libraries.

Open questions:

- When should a router switch between offline-augmented retrieval and online query expansion?
- Does capability-grounded retrieval still help when exact skill labels are themselves a weak proxy for downstream utility?
- How robust is the approach when community skill artifacts have noisy or inconsistent parameter structure?

## Memory lifecycle

| Stage | Design |
|---|---|
| **Write** | Start from an existing procedural skill and preprocess it into structured relations plus generated pseudo-queries. |
| **Organize** | Skill Knowledge Graph over capability, parameter, and example nodes; pseudo-queries remain tied to a functional point and valid invocation space. |
| **Read** | Use generated queries for offline index augmentation, online expansion, or retriever training; inject the selected skill into the agent. |
| **Update / forget** | Not studied; the paper does not address skill rewriting, consolidation, forgetting, or long-term governance. |

## Why it matters

Procedural-memory relevance is not the same as document relevance. If a skill library needs a routing layer, supervision should reflect the **execution contract inside the artifact**, not just its topic.
