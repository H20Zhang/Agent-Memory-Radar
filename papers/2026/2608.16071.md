# Skill2Query: Exploiting Skill Structure to Generate Pseudo-Queries for Agent Skill Retrieval

**arXiv:** [2608.16071](https://arxiv.org/abs/2608.16071) · **Published:** 2026-08-17 · **Category:** Retrieval & Access · **Importance:** 3/5 · **AI confidence:** High

**Tags:** `procedural` `structured` `text` `general-agent` · **Code:** [MatZaharia/Skill2Query](https://github.com/MatZaharia/Skill2Query)

> **TL;DR.** Skill2Query improves retrieval from large procedural-skill libraries by parsing each skill into capabilities, parameters, and examples before generating pseudo-queries. The useful result is not simply “synthetic queries help”: structured generation produces more functionally valid supervision, but online query expansion is inconsistent, and the end-to-end evidence is still a narrow one-step case study.

## Problem

Skill retrieval has a perspective mismatch. Users ask in task language—“what do I want to do?”—while SKILL.md-style documents describe developer-facing capability, parameter, and usage details. Plain semantic retrieval or document-level pseudo-query generation can therefore match the right topic while missing the exact function or constructing an invalid parameterization.

The supervision problem gets worse at scale: manually labeling query→skill pairs is expensive when thousands of candidate skills have overlapping descriptions.

## Core idea

Skill2Query first parses each skill document into a **Skill Knowledge Graph (SKG)** connecting:

- capabilities;
- parameters and constraints;
- usage examples.

It then generates pseudo-queries in three stages: imitate the user-query style from examples, generate templates anchored to specific capabilities, and fill/validate parameter slots from the schema. Those synthetic queries can support three deployment modes:

`skill document → structured pseudo-queries → offline index augmentation / online query expansion / retriever training → selected skill → agent execution`

The design goal is to create retrieval supervision that is **capability-grounded and parameter-consistent**, not merely semantically similar to the whole skill document.

## Memory design

| Stage | Design |
|---|---|
| Write | The persistent procedural artifact is an existing skill document; Skill2Query preprocesses it into structured capability/parameter/example relations and generated pseudo-queries. |
| Organize | Skill Knowledge Graph over Capability, Parameter, and Example nodes; each pseudo-query is tied to a functional point and valid parameter space. |
| Read | Use generated queries for offline index augmentation, online expansion, or training BM25/dense/SkillRouter retrieval; selected skills are injected into the downstream agent. |
| Update / forget | Not a lifecycle paper. It does not study skill rewriting, consolidation, forgetting, or long-term governance. |

## Compared to what

The pseudo-query baselines are **Zero-shot LLM**, **Few-shot LLM**, and a **SkillFlow-style** full-text generation condition. Retrieval is evaluated with **BM25**, a dense **SR-Emb-0.6B**, and a two-stage **SkillRouter**, each with baseline/offline/online variants.

That breadth is useful because it reveals that the method is not uniformly better under every serving choice.

## Evidence

Across retrieval settings, Skill2Query reports an average **+6.70 percentage-point Recall@1** gain.

The strongest retrieval gains appear where skill semantics are sparse or overlapping. On **ToolQA**, offline augmentation raises:

- SkillRouter R@1 **35.80% → 47.34%**;
- SR-Emb R@1 **13.22% → 29.79%**.

But the online mode is mixed. On **TheoremQA**, BM25 online expansion improves R@1 **60.37% → 65.19%**, while several LogicBench/ToolQA settings degrade. The right conclusion is therefore **offline and online semantic bridging solve different regimes**, not “online expansion is better.”

The generation ablation is more diagnostic. Removing the **Skill Knowledge Graph** drops Exec-Pass from **42.85% → 22.63%** and functional coverage from **11.32% → 2.41%**. That supports the claim that explicit capability/parameter structure improves the quality of synthetic supervision.

A 747-instance TheoremQA case study connects retrieval to downstream task success. Fine-tuned SkillRouter improves over no-skill by **+3.48pp** for GPT-5.4, **+8.57pp** for DeepSeek-V4-Flash, and **+3.34pp** for Qwen3.6-Plus. This is useful, but it remains one-step skill injection rather than a long-horizon tool-use evaluation.

## Why it matters

The interesting systems lesson is that **procedural-memory relevance is not document relevance**. A useful retriever needs to match a user request to the specific capability and valid invocation space inside a skill artifact.

That complements Demystifying Agent Skills: exact retrieval labels can be weak proxies for final utility, but if a skill library still needs a routing layer, retrieval supervision should at least be aligned to the internal execution contract rather than the outer document shell.

## Limitations / questions

- End-to-end evidence is limited to a one-step TheoremQA setup; it does not establish gains for long-horizon agents that invoke skills through tools and recover from failures.
- Online expansion is not reliably beneficial; some datasets/settings degrade, so serving-time adaptation needs a selector or switch condition.
- The method assumes reasonably standardized skill documentation with capabilities, parameters, and examples; noisy open-community skill stores may collapse the advantage.
- It improves access to an existing procedural-memory library rather than learning, consolidating, or governing that memory over time.

**Curator take:** **3/5**. Strong retrieval engineering with a real representation insight, but the contribution is narrower than a new agent-memory control boundary. The end-to-end evidence is preliminary and the online mode is not consistently positive.
