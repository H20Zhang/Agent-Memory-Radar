# D²ACCI：用可追溯证据决定 Memory Feature 是否应该被 Promote

[English](2608.17756.md) · [← 最新论文](../../README.md#latest) · [Research Library](../../library/README.md)

**Paper:** [arXiv:2608.17756](https://arxiv.org/abs/2608.17756) · **Importance:** 4/5

> **Research delta.** D²ACCI 不把 memory change 当成“benchmark 分数涨了就上线”，而是要求 paired baseline/candidate evidence、protected slices、stage trace 与 promotion gate 一起决定 `accept / monitor / feature-flag / reject`。

## 还没被解决的问题

Memory pipeline 可以在 ingestion、retrieval、filtering、context construction、generation、state update 任一 stage 失败。Aggregate score 告诉你“结果变了”，却常常不能回答**哪个 stage 造成了变化、哪类 case 被伤害、证据是否足以 promotion**。

## Mechanism

`instrumented run → typed stage traces → paired baseline/candidate outcomes → significance + protected slices + diagnostic coverage → accept | monitor | feature-flag | reject`

Null/rejected intervention 也被保留，不会从工程记忆里消失。

## 最近的公平比较

核心对照不是另一个 memory architecture，而是 **result-only evaluation**：同一个 intervention，如果 evaluator 必须保存 stage traces、paired statistics 与 non-regression constraints，决策会不会不同？

## 决定性证据

Supplement extraction **+2.71pp (p=.0009)**、session-memory retrieval **+3.67pp (p=.0026)**、Forget Guard **+1.92pp (p=.0030)**；相反 BM25/RRF 在 LoCoMo / LongMemEval 都统计不显著，因此只保留为 monitored feature flag。

60-case audit 中，trace-rich root-cause agreement 提升到 **κ=.571 fine / .619 coarse**，result-only 为 **.258 / .272**。

## 仍未证明什么

Diagnostic Coverage Rate 天然奖励 instrumentation，因此“trace-rich system 在 DCR 上更好”部分是定义导致的。真正更值得相信的 claim 是**promotion discipline 更严格、更可定位**，而不是 DCR 本身代表 user utility。协议目前也只在一个 instrumented stack 上展示。

## 对领域地图的影响

Memory evaluation 应从“哪个 architecture 分数高”转向**哪一个 stage 的 intervention 有 paired、localized、non-regressing evidence 足以被部署**。这让 negative/null result 也成为有价值的工程知识。
