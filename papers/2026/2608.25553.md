# When Stale Constraints Go Unchecked

[← Latest Papers](../../README.en.md#latest-papers) · [Research Map](../../README.en.md#field-map) · [Evaluation & Analysis](../../categories/evaluation-analysis.md) · [中文](2608.25553.zh.md)

**Paper:** [arXiv:2608.25553](https://arxiv.org/abs/2608.25553) · **Published:** 2026-08-26 · **Importance:** 4/5

> **Research delta.** This paper turns stale-memory failure into a **fixed-budget verification-allocation** experiment. Provenance remains correct; the variable is whether the consumer spends one of two available checks on the path that can reveal supersession.

## Problem

A consolidated constraint may be true when written and later withdrawn by a newer authoritative record. Keeping provenance does not help if a budget-limited agent never inspects that path before acting.

## Mechanism

A memory points historically to source `S0`; in superseded worlds `S1` later withdraws the constraint. The agent still inherits the stale one-line memory. Under `k=2` verification credits, the experiment compares native record choice with the same budget where one slot is re-assigned to the critical provenance path.

## Compared with

The decisive control is **native vs forced-critical at the same two-record budget**, plus valid-world controls where the source still agrees with memory. This is cleaner than comparing two different memory architectures.

## Decisive evidence

With the constraint stated, native agents inspect its provenance path in only 20.1% of primary and 23.1% of fresh-wording episodes. In superseded worlds, native decisions are stale-consistent in 77.3%, 74.7%, and 74.7% of primary, replication, and held-out episodes. Forced-critical allocation changes current-record-consistent decisions from `34/150→145/150` (+74.0pp), `38/150→147/150` (+72.7pp), and `38/150→130/150` (+61.3pp); a corrected held-out replication gives +73.3pp. When memory is still valid, forcing the same path changes outcomes by only 0–2pp.

## Main caveat

The intervention knows the critical path **from the experimenter**. It identifies how much error is due to allocation; it is not a deployable scheduler and does not show how often this stale-memory pattern occurs in production.

## Memory lifecycle

`write/consolidate S0 → preserve provenance → S1 supersedes S0 → inherited stale belief → choose 2 verification paths → act from inspected evidence`

The missing layer is freshness/supersession-aware verification allocation. Full index-maintenance, reconsolidation, dollar, energy, and privacy cost is not measured.

## Why it matters

Relevance and freshness are different control problems. A decision-relevant memory can be exactly the one the agent under-verifies. Future memory stacks should compare relevance-only access against deployable **cost-of-being-wrong / freshness-aware** verification under the same budget.
