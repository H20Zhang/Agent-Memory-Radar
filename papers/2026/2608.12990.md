# LycheeMemory V2: Efficient Long-Term Memory for LLM Agents via Semantic Segment-Level Consolidation

**arXiv:** [2608.12990](https://arxiv.org/abs/2608.12990) · **Published:** 2026-08-13 · **Category:** Write, Update & Consolidation · **Importance:** 4/5 · **AI confidence:** High

**Tags:** `semantic` `structured` `timeline` `general-agent`

> **TL;DR.** LycheeMemory V2 makes consolidation granularity a first-class systems knob: batching semantically coherent exchanges into segments cuts high-frequency LLM construction calls, while semantic rather than fixed boundaries preserve enough event/temporal structure to improve accuracy instead of merely trading quality for cost.

## Problem

Long-term memory construction is often **eager**: after each exchange, an LLM extracts facts, updates summaries, or revises memory. The cost therefore grows with every interaction. Simply consolidating less often is not sufficient, because mechanical windows or coarse summaries can group unrelated events and erase temporal/reference information.

The paper asks a more specific systems question: **at what granularity should expensive consolidation run?**

## Core idea

LycheeMemory buffers exchanges and finalizes a segment when embedding-based semantic surprise/cohesion indicates a boundary or a hard cap is reached. One LLM call then encodes the entire finalized segment into context-independent typed records. A small amount of same-session reference context is carried forward only to disambiguate entities and references, not to invent new facts.

Records retain entities, topics, temporal scopes, provenance, and the source segment's event-frame identity. At query time, a planner chooses typed recall routes over semantic records, entity/topic/time/event-frame indexes, and raw turns. Retrieval, fusion, reranking, and diversity selection are deterministic after planning.

## Memory design

| Stage | Design |
|---|---|
| Write | Buffer exchanges → detect semantic boundary → one LLM encoding pass per finalized segment; average 5.8 turns/segment on LoCoMo. |
| Organize | Typed self-contained records in an append-only store with entity, topic, temporal, entity-topic, and event-frame evidence indexes plus provenance. |
| Read | Query planner → typed recall routes → semantic/structured/raw-turn retrieval → fusion/reranking/diversity selection → compact evidence. |
| Update / forget | Append-only in this work; consolidation frequency is adaptive, but contradiction repair, deletion, and forgetting are not central. |

## Compared to what

The strongest evidence comes from **construction-side controls inside the same framework**:

- **Eager consolidation** removes batching but keeps the rest of the design.
- **Fixed-window consolidation** keeps batching but replaces semantic boundaries with mechanical windows.

This cleanly separates two claims that would otherwise be conflated: batching reduces construction cost; semantic boundaries preserve quality.

The paper also compares against A-Mem, Mem0, TiMem, MemoryOS, and other conversational-memory systems.

## Evidence

On LoCoMo with GPT-4.1-Mini, full LycheeMemory reaches **89.22** accuracy with **204.1K** construction tokens. Eager construction rises to **849.9K** tokens (**+316%**) while accuracy falls to **81.88**. Fixed-window batching uses slightly fewer tokens (**174.7K**) but accuracy falls to **82.40**.

That is the key ablation: **batching is the cost mechanism; semantic segmentation is the quality mechanism**.

Relative to A-Mem, construction tokens fall **86.0%** on LoCoMo and **75.9%** on LongMemEval-S. Query tokens also fall (LoCoMo **4.01K vs 5.56K** for A-Mem), so the accuracy gain is not bought by moving the same cost to a larger answer-time context.

The rest of the pipeline is not incidental. Summary-level records score **80.78**, record-vector-only retrieval **81.75**, and removing fusion/reranking/diversity drops to **66.62**, versus **89.22** for the full system.

## Why it matters

Memory efficiency has at least three independent knobs: **what gets retained, how it is accessed, and how often expensive transformation runs**. LycheeMemory is important because it isolates the third. A system can reduce LLM construction frequency without reverting to lossy coarse summaries if consolidation boundaries follow coherent events rather than arbitrary turn counts.

The comparison to Total Recall is useful: serving economics are lifecycle-wide, and this paper attacks one concrete source of that lifecycle cost—the frequency of write-side LLM work.

## Limitations / questions

- Evaluation is text-only conversational QA, not acting agents or multimodal long-term memory.
- Token accounting does not establish production latency, database/index storage, cache behavior, or monitoring cost.
- Preference-heavy questions remain weaker than systems with explicit profile/persona modeling.
- Boundary quality may depend on embedding model, threshold, and conversation style; cross-domain robustness is not established.

**Curator take:** **4/5**. The important contribution is not another typed memory schema. It is the causal decomposition of **consolidation frequency versus segmentation quality**, with a strong cost/accuracy ablation showing why semantic batching can be better than both eager updates and fixed windows.
